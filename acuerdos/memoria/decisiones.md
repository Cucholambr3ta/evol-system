# Decisiones clave

> Atomo de MEMORY. Decisiones de arquitectura y producto persistentes.

- **Registro de disciplinas 9→31** (2026-06-05, v0.3.2): el sistema integra 31 metodologias *-Driven (9 base + 22 extendidas), heredadas del upgrade X-DD `ultimate-update.md`. Registro canonico en `docs/disciplinas/INDEX.md`. 0 colisiones de ID.
- **Activacion por profile, no global:** cada proyecto declara su subset en `evol.profile.yml` (bloque `methodologies:`); el orquestador inyecta solo esas capas en su fase, resuelve el DAG de dependencias (ej. chaos exige odd_obs+threat_driven), y aplica los criterios como sub-gate. No se inyecta lo no declarado.
- **0 agentes permanentes nuevos:** las disciplinas se ejecutan con los 16 agentes core + efimeros (evol-agent-factory). El core permanente NO crece con el upgrade.
- **3 formas de integracion por disciplina** (campo `executor` en la ficha): mapeo a workflow existente, skill nueva (6 gaps: ux-driven, event-sourcing, api-versioning, iac-driven, debt-budget, use-case-driven), o capa declarativa (regla/sub-gate sin workflow).
- **Erradicación de Memoria Persistente (2026-06-06):** Se retiró Memoria Persistente y todo el "Modo COMPLETO" legacy de X-DD. La memoria queda gobernada por la Standard Library de Python en "Modo BASE" puro. Posteriormente se implementó EDMS completo (v0.6.0) con ChromaDB + NetworkX.
- **Skill readme-master como gate de calidad documental (2026-06-06, v0.5.0):** La skill `/evol readme-master` es el estándar oficial para cualquier archivo README.md del proyecto. Opera recursivamente sobre todos los subdirectorios y es activada automáticamente por el hook `pre-push` de `evol-gitflow.sh`. Los READMEs deben seguir el patrón Top 100 (HTML grid, Mermaid obligatorio, badges, sin emojis).
- **memory/ como directorio de runtime local (2026-06-06, v0.5.0):** La carpeta `memory/` (con `memory/raw/`) es un directorio de runtime local, ignorado por git por diseño. Debe ser creada por `evol-init.sh` en el bootstrap con permisos `750`. Nunca se versiona.
- **release-close como gate de memoria (2026-06-06, v0.5.0):** Todo release debe invocar `evol-gitflow.sh release-close --version=X.Y.Z` ANTES del tag git. Este comando dispara la actualización de `acuerdos/memoria/` y la sincronización de `MEMORY.md`. Sin este paso, la memoria persistente queda desactualizada respecto al estado real del repositorio.
- **Erradicación de GitNexus (2026-06-06):** Se eliminó GitNexus del framework completo (docs, configs, workflows). 17 archivos modificados, -435 lineas. Referencias residuales en `evol-agent-lifecycle.py` y `evol-evolve.py` protegidas por env var `EVOL_GITNEXUS=1` (inactivas por defecto). Razon: licencia PolyForm NC incompatible con uso comercial + requiere MCP.
- **Arquitectura EDMS: ChromaDB + LadybugDB global (2026-06-06, v0.6.1):** Memoria nativa implementada con ChromaDB (vector semántico) + LadybugDB (graph/relacional) en una DB global `~/.evol/memory/` (no per-project). Separación por metadata, no por DB. 15 mejoras investigadas (24 repos analizados). Plan atómico en `docs/plan-implementacion-edms.md`. **v0.6.1 completado** — 6 fases + expanded indexing, 52 tests, installer cross-platform.
- **Discipline-aware schema como diferenciador único (2026-06-06):** El schema de metadata de EDMS incluye `disciplinas[]` como multi-value filter — ningún otro framework de memoria maneja 31 disciplinas *-Driven como filtro de memoria. Habilita queries como "qué decisiones afectan SEGURIDAD?" o "qué lecciones de DDD hay?".
- **RRF fusion + composite scoring (2026-06-06):** Retrieval híbrido usa Reciprocal Rank Fusion (k=60) para fuscionar 3 streams (BM25 + Vector + Graph) con composite scoring (salience + recency + importance). Decay adaptativo por tipo de memoria. Referencia: agentmemory (95.2% R@5).

- **LadybugDB + ChromaDB como data stack principal (2026-06-06, v0.6.1):** LadybugDB (`pip install ladybug`, v0.17.1) es la graph database principal. ChromaDB es el vector store. NetworkX queda como fallback ligero. Grafo persiste en `~/.evol/memory/ladybug.lbug`. - **EDMS v2.0 Memory Architecture: 4 phases complete (2026-06-07):** Investigación multi-repo (GBrain, Mem0, Letta, Supermemory, MemPalace, GitNexus) → implementación de 4 fases: (1) Fundamentos (verbatim store, ADD-only extractor, auto-linker zero-LLM, entity store temporal), (2) Recuperación Híbrida (BM25 Okapi stdlib, evidence contracts, graph expander, hybrid retriever RRF k=60), (3) Consolidación (reflection engine, dreaming sprint-aware, forgetting con TTL/grace-period/dry-run, conflict detector predicate/temporal/factual), (4) Portabilidad (agent file format portable, relational intelligence scores, REST API stdlib, migration tool v1→v2 con snapshots). 18 componentes, ~4600 líneas, 137 tests, 0 dependencias externas.
- **Verbatim storage como principio fundamental (2026-06-07):** Toda memoria se almacena en forma verbatim original. Embeddings y resúmenes se generan como cache separada, nunca como sustitución. Content hash SHA-256 para integridad. Preserva fidelidad y permite regenerar embeddings sin pérdida.
- **ADD-only extraction sin LLM (2026-06-07):** Entity extraction usa regex rules-based (8 tipos: technology, project, concept, discipline, agent, person, file, metric, date). Zero tokens LLM. Contradicciones coexisten, retrieval ranking maneja staleness. Más simple y robusto que diff-then-merge.
- **Auto-enlace zero-LLM en cada escritura (2026-06-07):** 7 patrones de enlace (PARA, CON, USANDO, BASADO_EN, SEPARADO_DE, DEPENDE_DE, COMPLEMENTA) + semantic proximity. Grafo crece a costo ~0. No requiere LLM para indexación básica.
- **Hybrid retrieval con RRF fusion (2026-06-07):** BM25 Okapi stdlib + vector search (ChromaDB) + graph expansion. Reciprocal Rank Fusion (k=60) combina 3 streams. Evidence contracts adjuntos a cada resultado con source, temporal validity, confidence.
- **Controlled forgetting con dry-run (2026-06-07):** TTL configurable (default 90d), min_access_count (default 2), min_relevance (default 0.3), grace_period (default 30d). Dry-run mode para validación antes de borrar. Backup antes de cada ciclo de consolidación.
- **Agent file format para portabilidad (2026-06-07):** Snapshots inmutables de memoria de agente con checksum SHA-256. Merge de snapshots del mismo agente. Diff entre snapshots. Inspirado en Letta. Permite transferir memoria entre sistemas.
- **Relational intelligence precomputada (2026-06-07):** Scores de relación agente-agente, agente-proyecto basados en patrones de interacción. Sugerencia de colaboradores para tareas. Persistencia en JSON.
- **Migration tool con snapshots (2026-06-07):** Migración EDMS v1→v2 con checksums, dry-run mode, y rollback via snapshots. Verificación de integridad post-migración. One-way pero reversible.
