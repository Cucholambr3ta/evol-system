# Convenciones

> Atomo de MEMORY. Estandares de codigo y patrones del proyecto.

- **Citacion de fuentes (DOC_STANDARD 1.7):** todo claim producto de investigacion web lleva el link de su fuente. Sin URL = INCOMPLETO. Enforced en discovery/doc-granular/research + las 31 fichas (seccion Fuentes) + `validate-disciplinas.py` (bloquea ficha con `fuentes[]` vacio). El sidecar `.json` captura las URLs via `evol-doc-sync.py` `_extract_sources()`.
- **Labels Mermaid:** salto de linea = `<br/>` (nunca `\n`); todo label con caracteres especiales `() / — ' "` va entre comillas dobles `["..."]`, incluido `subgraph ID["..."]`. El bundle browser de Mermaid es mas estricto que `mmdc` CLI — verificar con el engine del consumidor. Ver `lecciones.md`.
- **Copias reales, nunca symlinks** para `.claude/commands/`, `.github/prompts/`: los IDEs AI-agent no siguen symlinks. SSoT en `.agent/workflows/`; el adapter materializa copias.
- **README.md estandar Top 100 (v0.5.0):** Todo README.md del proyecto (raiz y subdirectorios) debe cumplir el estandar definido en `skills/readme-master/SKILL.md`: HTML centrado, badges Shields.io con iconos, tabla comparativa, Core Features con bloques de codigo, diagrama Mermaid de arquitectura, y seccion de Instalacion/Desinstalacion. La skill opera recursivamente.
- **release-close es obligatorio en todo release (v0.5.0):** El paso `evol-gitflow.sh release-close --version=X.Y.Z` debe ejecutarse ANTES del `git tag`. Es el unico mecanismo que conecta el flujo de release con la actualizacion automatica de `acuerdos/memoria/` y `MEMORY.md`.
- **Planes de implementacion atomicos (2026-06-06):** Los planes de implementacion se guardan como archivos markdown atomicos en `docs/plan-*.md`, no en memoria.md ni en AGENTS.md. Un solo archivo por plan, con todas las secciones (arquitectura, schema, hooks, tests, fuentes). Referencia: `docs/plan-implementacion-edms.md` (720 lineas, 18 secciones).
- **Research-first antes de implementar (2026-06-06):** Antes de implementar un subsistema complejo, investigar al menos 10 repositorios de referencia y documentar mejoras en un plan atomico. El plan se aprueba ANTES de escribir codigo. Evita reimplementar lo que ya existe y captura patrones de la industria.
- **Privacy stripping obligatorio antes de indexar (2026-06-06):** Todo texto que entre a ChromaDB o NetworkX debe pasar por `privacy_strip()` primero. Eliminar API keys, tokens, passwords, private tags. Nunca indexar secrets. Referencia: Secure Memory MCP (84 tests de seguridad).
- **Sincronización recursiva de documentación (2026-06-06):** Al realizar operaciones de sincronización de sidecars JSON, se debe correr `sync-folder` explícitamente en directorios anidados de segundo nivel (como `docs/arquitectura/adr/` y `docs/usuario/comandos/`), ya que la llamada a `sync-all` predeterminada no los escanea de forma recursiva profunda.
- **Aislamiento de la carpeta `acuerdos/` (2026-06-06):** El directorio `acuerdos/` actúa como Flight Recorder y almacena la evidencia del pipeline agéntico (ideación, discovery, wireframes y logs de memoria local). Es local y se ignora en Git por diseño para no ensuciar la base del producto, diferenciándose de las especificaciones y guías oficiales (`/docs`, `/spec`, `/plan`).
- **Gobernanza Criptográfica del Pipeline (2026-06-06):** Los gates de fase son inmutables para el agente debido a la firma HMAC-SHA256 encadenada en `evol-gate`. Ningún agente puede saltarse pasos de forma unilateral; los overrides (`EVOL_SKIP_*`) son de uso exclusivo del usuario humano.
- **LadybugDB como graph database (v0.6.1):** Grafo se persiste en `~/.evol/memory/ladybug.lbug` usando LadybugDB (`pip install ladybug`). NetworkX queda como fallback ligero. Dependencia optional via `pip install evol-dd[graph]`. Sin ladybug, grafo usa networkx o se omite silenciosamente.
- **Optional-dependencies en pyproject.toml (v0.6.1):** `memory` = chromadb, `graph` = ladybug + networkx, `full` = ambas. `pip install evol-dd` base funciona sin ninguna de las dos. Fallback stdlib siempre disponible.
- **Tier system para consolidación (v0.6.0):** Items se clasifican en tiers: raw→compressed→memory→knowledge→archived. Cada tier tiene decay adaptativo por tipo de memoria. Campo `tier` en metadata de ChromaDB, no prefijo en texto.
- **Installer cross-platform (v0.6.0):** `install.sh` es la forma oficial de instalar Evol-DD. Detecta OS/Python/pipx automáticamente. Soporta Linux/macOS/WSL. Flags: `--no-ide`, `--dry-run`.
- **aesthetic_profile gobierna el diseño (2026-06-06):** `evol.profile.yml` declara `aesthetic_profile: bold | enterprise-minimal`. Las skills `evol-frontend-design` y `evol-remotion` lo leen para decidir la dirección estética. Si no está declarado, la skill pregunta — nunca asume. EDMS usa `enterprise-minimal` (Linear/Vercel/GitHub Projects, paleta `#0F1115`/accent `#4F46E5`, monocromático, sin glassmorphism, sin emojis, Geist/Inter).
- **MCP gestionado por evol-mcp.sh (v0.6.0):** Los servers MCP se registran con `bash scripts/evol-mcp.sh add <name> <cmd> [args]`, se listan con `list`, se quitan con `remove`, se verifican con `status`. La config vive en `evol.config.yml` (`mcp.enabled: true`). Context7 registrado como `context7 → npx @upstash/context7-mcp`.
- **CSO en descriptions de skills (2026-06-06):** La `description` del frontmatter describe CONDICIONES de trigger, no el workflow. Si detalla el procedimiento, el agente sigue la description en vez de leer el SKILL.md. Formalizado en `crear-skill` junto con RED-GREEN-REFACTOR (test-first). Inspirado en obra/superpowers.
- **Base64 encoding para properties en LadybugDB (v0.6.1):** LadybugDB interpreta strings JSON como Cypher map literals. Properties se almacenan como `base64.b64encode(json.dumps(props).encode()).decode()`. Decode al leer con `json.loads(base64.b64decode(encoded).decode())`.
- **MERGE en vez de CREATE para nodos (v0.6.1):** LadybugDB falla con `CREATE` si el nodo ya existe (duplicate PRIMARY KEY). Usar `MERGE` para nodos con `name` como PRIMARY KEY. `CREATE` solo para relaciones.
- **importance + content_hash como metadata estándar (v0.6.1):** `index()` auto-agrega `importance=0.5` (float 0-1, default) para composite scoring weight y `content_hash` (SHA-256[:16]) para change detection. Ambos campos son parte del schema estándar de EDMS.
- **NDJSON traces para real-time monitoring (v0.6.1):** Todo evento EDMS (index, search, graph op, session start/end) se emite como NDJSON a `.evol/traces/<session-id>.jsonl`. Formato: `{"ts":"ISO8601","event":"name","session_id":"...","agent":"...","project":"...","data":{...}}`. Append-only, rotación 10MB/50 archivos. Stdlib Python, 0 dependencias.
- **SSE server stdlib para real-time monitoring (v0.6.1):** `evol_sse_server.py` usa `http.server` stdlib (no FastAPI) para streaming de eventos via Server-Sent Events. Endpoints: `/api/v1/events` (SSE stream), `/api/v1/state` (project state), `/api/v1/loops` (loop alerts), `/` (dashboard HTML). Puerto configurable via `EVOL_SSE_PORT`.
- **v2 components stdlib-only (2026-06-07):** Todos los 18 componentes de EDMS v2.0 usan Python stdlib (json, hashlib, re, collections, dataclasses, http.server). 0 dependencias externas nuevas. ChromaDB y LadybugDB siguen siendo opcionales para vector/graph search.
- **Evidence contracts en cada resultado de búsqueda (2026-06-07):** Todo resultado de hybrid_search incluye EvidenceContract con: sources (type, id, confidence), temporal (valid_from, valid_to), reasoning, confidence score. Permite auditoría completa de por qué un resultado es relevante.
- **Conflict detector: 3 tipos de análisis (2026-06-07):** Predicate contradictions (A and not A via negation patterns), temporal inconsistencies (contradictions within time window), factual contradictions (different values for same topic). Resolución: keep_latest, keep_highest_confidence, manual.
- **Forgetting: grace period obligatorio (2026-06-07):** Nunca olvidar items dentro del grace_period_days (default 30). Dry-run mode por defecto en nuevos installs. Backup antes de cada ciclo de consolidación. max_forget_per_run limita cantidad por ciclo.
- **Agent file: checksum obligatorio (2026-06-07):** Todo AgentMemorySnapshot tiene checksum SHA-256 calculado sobre contenido. Load verifica integridad y falla si checksum no coincide. Merge preserva checksums originales.
- **Migration: snapshot antes de migrar (2026-06-07):** Toda migración v1→v2 crea snapshot completo antes de escribir. Rollback = restaurar snapshot. Verificación post-migración con checksums.
- **HybridRetriever: BM25 + vector + graph (2026-06-07):** Búsqueda híbrida usa 3 streams fusionados con RRF (k=60). Cada componente es independiente y desactivable via flags (use_vector, use_bm25, use_graph). Fallback graceful si componente no disponible.
- **v2 persistence hooks en boundaries de sesión (2026-06-07):** `session:start:memory-dreaming` ejecuta `DreamingEngine.dream()` al inicio (estandar). `session:end:memory-persistence` ejecuta `ReflectionEngine.reflect()` + `ForgettingEngine.find_candidates()` + `ConflictDetector.detect()` al final (estricto). Los hooks usan `evol-memory.py` como entry point.
- **npm wrappers: PYTHONPATH=scripts (2026-06-07):** Los 15 wrappers en `bin/` ejecutan `python3 -c "from evol_cli import main; main()"` con `PYTHONPATH=scripts` para resolver imports de scripts locales como `_evol_common.py`. Patrón: wrapper en JS → Python entry point → runpy dispatch.
- **Skills local-only no se distribuyen (2026-06-07):** `revision-release`, `update-context`, y `update-memory` viven en `~/.agents/skills/` pero NO están en `pyproject.toml`, `package.json`, ni `CATALOG.json` del paquete. Son skills personales del usuario, no parte del framework distribuible.
- **attributionLogo false por defecto en code-gen (2026-06-07):** Skills de generación de código (lightweight-charts, etc.) generan código con `attributionLogo: false` por defecto. Los proyectos del usuario no muestran branding de terceros. Override explícito requerido si se desea el logo.

- **TUI: graphs con fallback ASCII obligatorio (2026-06-08):** Toda pantalla TUI que renderiza grafos (`knowledge_graph.py`, `dev_graph.py`) envuelve la construcción netext/networkx en try/except (ImportError + AttributeError por API mismatch) y cae a representación ASCII estática. Garantiza que la app corre incluso sin deps de grafo o con versión incompatible de netext.
- **TUI: 13 temas como archivos TCSS independientes (2026-06-08):** Cada tema vive en `styles/themes/<nombre>.tcss` (~15-25 líneas, solo overrides de variables: $primary, $surface, $background, $text, $accent, $success/warning/error). `ThemePicker` cicla con `T`, aplica releyendo el archivo. Nombres: bruma/lavanda/marfil/ambar/nocturna/bosque (i18n previos) + grafito/salvia/coral/pizarra/oceano/arena/violeta (nuevos, claros vs oscuros balanceados).
- **EDMS Web PWA: todos los gráficos en 3D (2026-06-08):** Knowledge graph, GitFlow tree, y los 4 charts de Analytics se renderizan como escenas ThreeJS con controles orbitales (rotar, zoom, pan). RT Monitor usa 3D surface chart. Cada card con gráfico 3D permite al usuario explorar los datos desde cualquier ángulo.
- **Onboarding Guide: blur sin afectar sidebar (2026-06-08):** El backdrop del Onboarding Guide aplica `backdrop-filter: blur(8px)` solo sobre el contenido de la página (left = sidebar-width). El sidebar siempre permanece interactivo y sin blur. Z-index: sidebar (102) > guide-card (101) > guide-backdrop (100).
- **update-memory y update-context: git pull obligatorio (2026-06-08):** Ambos workflows ejecutan `git pull --ff-only` como Step 0 antes de leer cualquier archivo. Si hay conflictos de merge, el agente se detiene y pide resolución. Previene pérdida de datos en escenarios multi-agente/multi-workspace.
- **ui-ux-pro-max como skill global, no del paquete (2026-06-08):** La skill de diseño UI/UX vive en `~/.agents/skills/ui-ux-pro-max/` pero NO está en el paquete evol-dd. Es una skill personal del usuario para uso multi-proyecto. Se actualiza via `uipro update`.
- **21st.dev MCP en opencode.jsonc (2026-06-08):** El MCP server `@21st-dev/magic` se configura en `~/.config/opencode/opencode.jsonc` bajo `mcpServers`. La API key va en `env.API_KEY`. No se commitea al repo — es configuración local del usuario.
